# Architecture

A single Python package (`src/hometracker`) with an argparse CLI, run by Docker Compose on a single machine. This page describes what is implemented (stage 1); the target design for later stages is in the [plan](plan.md).

## Containers

| Service | Image | Role | Published |
| --- | --- | --- | --- |
| `db` | `postgres:16-alpine` | the database (`pgdata` volume) | not published |
| `worker` | built from `Dockerfile` | `hometracker loop`: collection, matching, dedup, alerts | not published |
| `ntfy` | `binwiederhier/ntfy` | push notifications for the phone (`ntfydata` volume) | `127.0.0.1:8090` |
| `web` | built from `Dockerfile` | `hometracker web`: feed and apartment pages, read-only ([ADR 0004](engineering/decisions/0004-web-interface.md)) | `127.0.0.1:8080` |

`./data` and `./profiles` are bind-mounted into the worker, and read-only into `web`. Outside access is a tunnel configured outside this repository (for example Cloudflare Tunnel) that routes one hostname to ntfy and, later, one behind Cloudflare Access to the web interface. See [ADR 0001](engineering/decisions/0001-docker-compose.md).

## Data flow

```
profiles/*.yaml ──> pipeline ──> adapter.search(url) ──> PoliteClient ──> platform
                       │              │                     └──> data/raw/<host>/<day>/*.html.gz
                       │              └─ fetch_detail() for new listings that pass the filters
                       ▼
                 profiles.match() ──> photos (data/photos/, pHash/dHash) ──> dedup.assign_property()
                       │
                       ▼
                 listing / listing_snapshot / photo / property ──> alert ──> Notifier (ntfy, email)
```

- **Adapters** (`adapters/`, one module per platform, registered in `adapters/__init__.py`: Storia, OLX, Imobiliare.ro, Publi24 from its JSON-LD, Lajumate from its `__NEXT_DATA__`) turn search and detail pages into `ListingData` (`schema.py`). Parsing is done by `parse_search(html, url)` and `parse_detail(html, url)`, which do no I/O; fetching goes through `Adapter.search` / `fetch_detail` and the shared `PoliteClient` (`http.py`), which serializes requests per host, waits a random delay and archives the raw HTML.
- **Parsing helpers** (`parsing.py`) interpret Romanian text: price and currency, floor, area, rooms, balcony, phone numbers.
- **Profiles** (`profiles.py`) load `profiles/*.yaml` and compute hard filters plus a 0–100 preference score with reasons.
- **Dedup** (`dedup.py`) scores a new listing against every listing already attached to a property and joins the best property if the combined score reaches `MATCH_THRESHOLD` (0.75). Signals and fixed weights: photos in common (pHash ≤ 8, or pHash ≤ 12 confirmed by dHash ≤ 8; two or more 0.75, one 0.45), text similarity (Jaccard on 3-word shingles after normalization, ignoring shingles shared by more than 5 listings as agency boilerplate; ≥ 0.5 → 0.4, ≥ 0.3 → 0.25), the same phone (0.2), area within 2 m² (0.15), same floor (0.15), same rooms (0.05), coordinates within 300 m (0.05). A known contradiction vetoes the pair: area apart by more than 5 m², another floor, other rooms, more than 1 km apart. Without photos in common, a pair also needs an identity signal (the same phone or close coordinates), because agency boilerplate is only recognized after a few listings. The phone counts only for non-agency publishers whose number is not already on several properties. The listing records `match_reason` (`new` or `score`), `match_signals` (for example `photos:2,text:0.62,area,floor`), `match_score`, `shared_photos` and `matched_listing_id`. Photo embeddings (CLIP + pgvector) are not used; they would need a decision record. A listing attached to an existing property is a **republication** (`listing.republished_from_id`) when an earlier listing of the same property, on the same platform, has the same publisher (phone hash, else normalized publisher name). Listings without a known publisher are never marked, because the owner and an agency that copied the photos would look the same.
- **Publishers** (`publishers.py`) identify who publishes: the phone hash, else the normalized publisher name (`publisher_key`, also used for republications). The pipeline links every listing it handles (`listing.publisher_id`) and, at the start of each run, the listings stored before or without a link. The declared type is what the listings say; once a publisher declared itself an agency it stays one. Statistics are computed on demand: listings, active listings, apartments, platforms, listings **taken over** (the apartment first appeared at another publisher), the average price difference to the cheapest active listing of other publishers for the same apartment, and a **possible agent** flag for a declared owner whose identity is on `DISGUISED_AGENT_PROPERTIES` (5) or more apartments.
- **Authenticity** (`authenticity.py`) scores an apartment 0–100, always with the signals that produced it: 100 minus 30 per large, 15 per medium, 5 per small signal. Large: the same photos at 3+ publishers; an agency publishing after the first appearance of another publisher; the cheapest active price per m² more than 15% under the median of at least 5 comparable apartments (same rooms, ground floor or not), otherwise a note says the price cannot be compared yet; a publisher flagged as possible agent; an active listing reusing the photos of a listing that disappeared 30+ days before it appeared. Medium: 2+ republications over 90+ days at one price. Small: 5+ photos but a missing floor, area or address; the same publisher at different prices on different platforms. Instant alerts carry the score and signal labels, and a profile can require `notify.min_authenticity` (default 0); a blocked alert is not recorded, so it can still go out later. The web feed and apartment page show the score and the explained signals.
- **Labels** (`labels.py`) are what the maintainer sets in the interface: saved, hidden, verdict (`real` / `fake`) per apartment in `property_label`, and every action in `label_event` (for calibrating the weights later). "Not the same apartment" (`split_listing`) moves a listing into a new apartment (`match_reason = manual`) and clears republication links that went through it. Effects: price-drop alerts go only to saved apartments when the profile's `notify.price_drop_scope` is `saved` (the default, as in the plan; `alerted` keeps the stage 1 behavior); hidden and fake apartments get no alerts and leave the daily summary; a `real` verdict lets an alert through below `min_authenticity`.
- **History** (`history.py`) assembles a property's history on demand: its listings in order of appearance (the first one is usually the original source), publishers and prices, the price timeline from `listing_snapshot`, republications and days on market (from the first appearance until today, or until the last listing disappeared).
- **Construction year** (`buildyear.py`, `osm.py`, [ADR 0005](engineering/decisions/0005-openstreetmap-buildings.md)) estimates an interval for the block, always with the evidence behind it, on demand: OpenStreetMap `start_date` of the nearest building within 30 m (confidence `mare`; listings that disagree are shown as conflicts), else years declared by the listings (the platform's field or text such as "an construcție 1978"), also from other apartments within 40 m (the same block); two or more listings agreeing within 2 years give `medie`, one gives `mică`; else decades in the text ("anii '70") and the block typology (panels 1962–1990, brick P+4 1955–1990, P+8 or higher 1968–1990, new build 2005+). The worker queries Overpass for at most `OSM_LOOKUPS_PER_RUN` (5) uncached locations per run, with the project's own User-Agent; results, including "nothing found", are cached in `osm_building` by coordinates rounded to 4 decimals and never refetched. A block or error from Overpass stops the lookups for that run. Other sources are described in [surse-an-constructie.md](surse-an-constructie.md).
- **Pipeline** (`pipeline.py`) runs a profile across its sources, stores listings and snapshots, downloads photos for matching listings, assigns properties, sends alerts and warns when an adapter errors or returns nothing. After the searches it rechecks matched listings that have left the search results (see below), then runs the OpenStreetMap lookups.
- **Notifications** (`notify.py`): ntfy (JSON publish, token auth) and SMTP email. A profile can send to its own `notify.ntfy_topic` and `notify.email_to` (validated: ntfy topic characters, addresses without line breaks); without them, `NTFY_TOPIC` and `EMAIL_TO` from the environment. Alerts, collection warnings and the daily summary all use the profile's destinations; `hometracker test-notify --profile <name>` checks them.
- **Daily summary** (`summary.py`): after each run in `loop`, a profile whose summary is due (first run after `SUMMARY_HOUR` local time, once per local day) gets a message on `notify.summary_channels` (email by default) covering the period since the last summary (24 h the first time, at most 7 days): new listings that passed the filters but stayed under the alert threshold, listings that disappeared, republications, collection gaps longer than two intervals, and the number of instant alerts sent. A summary that no channel delivered is not recorded and is retried at the next run. ntfy gets a shortened body.
- **Web** (`web.py`, `templates/`): FastAPI with Jinja2 rendered on the server, no JavaScript. `/` is the feed for a profile (apartments with at least one listing that passes the profile, ordered by the profile score; `?removed=1` includes apartments no longer active), `/property/{id}` the apartment page (listings, publishers, match signals, construction year with its evidence, price chart as inline SVG, price table, photos), `POST /property/{id}/label/{action}` and `POST /listing/{id}/split` the label buttons (plain HTML forms with a redirect; refused unless `Origin` or `Referer` matches the host, against cross-site requests), `/publishers` the publishers with their statistics, `/publisher/{id}` one publisher's listings (taken over, republished), `/photo/{id}` a local photo, only if its stored path is inside `data/photos`. Listing links are rendered only for `http(s)` URLs. Apart from the label buttons, the app only reads.
- **Demo data** (`demo.py`): `hometracker demo` fills an empty database with synthetic apartments, for working on the interface (`DATA_DIR=data/demo`, preview configuration `web-demo` in `.claude/launch.json`).
- **CLI** (`cli.py`): `loop`, `run [--catchup]`, `summary [--print]`, `property <id|url>`, `web`, `demo`, `dump <url>`, `test-notify`, `matches`.

## Tables and ownership

All tables are defined in `models.py` and written by the worker only.

| Table | Written by | Holds |
| --- | --- | --- |
| `listing` | `pipeline.py` | one listing on one platform, unique per `(platform, external_id)`; `phone_hash`, never the phone; `active`, `checked_at` and `removed_at` from the recheck |
| `listing_snapshot` | `pipeline.py` | the listing's price when first seen and at every change |
| `photo` | `pipeline.py` | downloaded photos: source URL, local path, pHash, dHash |
| `property` | `dedup.py` | the physical apartment (cluster); listings point to it through `listing.property_id`, with `match_reason`, `shared_photos` and `republished_from_id` on the listing. The plan's separate `property_listing` table is not used: a listing belongs to exactly one apartment, so the link and its reason live on the listing |
| `publisher` | `publishers.py` | who publishes: `key` (phone hash or normalized name), name, declared type, first and last seen; listings point to it through `listing.publisher_id` |
| `alert` | `pipeline.py` | sent notifications per profile, property and kind (`new`, `price_drop`) |
| `property_label` | `labels.py` | saved, hidden and verdict per apartment |
| `label_event` | `labels.py` | every label action, with the listing for "not the same apartment" |
| `osm_building` | `osm.py` | cached Overpass lookups: rounded coordinates, nearest building id, `start_date`, `building:levels`, `fetched_at` (also when nothing was found) |
| `summary_log` | `summary.py` | one row per daily summary delivered: profile, covered period, channels |
| `run_log` | `pipeline.py` | one row per profile and platform run: counts and errors, used for warnings and catch-up |

## Key conventions

- **Prices** are kept as published (`price`, `currency`) and converted to `price_eur` with the `EUR_RON` setting; filters and alerts use `price_eur`.
- **Floors** are strings: `basement`, `ground`, `raised_ground`, `1`, `2`, …, `attic`; `None` means unknown, which a profile may allow.
- **Unknown is not false**: `balcony`, `area_m2`, `rooms` and `floor` stay `None` when the page does not say.
- **Recheck**: a listing seen in search is confirmed by the search itself (`last_seen`). A listing that passed a profile (`property_id` set), is still `active` and has not been seen in search for `RECHECK_AFTER_HOURS` (24) gets its detail page fetched again, at most `RECHECK_PER_RUN` (10) per run and once per period (`checked_at`). A new price goes through the same snapshot and price-drop rules as the search. HTTP 404/410, or `Adapter.is_removed` on the page, marks the listing `active = False` with `removed_at`; it becomes active again if it reappears in search. Other errors leave it active and retry next period; a block stops the recheck for that platform. Expired-listing behavior checked on real pages (October 2026): Storia answers an expired listing with HTTP 410 and `ad.status` = `removed_by_user`, a nonexistent one with 404, an active one with `ad.status` = `active`; `StoriaAdapter.is_removed` also catches those states if a page comes with 200. OLX answered every request, including search pages, with HTTP 403 from CloudFront, so its expired-listing shape is unknown and the source is disabled in the profile (`enabled: false`) until there is a permitted way to collect it; Imobiliare.ro has not been checked. Both keep the default `is_removed` (`False`) and rely on 404/410.
- **Catch-up**: after a gap longer than two intervals (Mac asleep or off), the next run reads `PAGES_CATCHUP` result pages instead of `PAGES_NORMAL`.
- **Local files**: `data/raw/` (gzipped HTML), `data/photos/`, `data/debug/` (pages saved by `dump`). Without `DATABASE_URL`, the app uses SQLite at `data/hometracker.db`.

## Schema evolution

`init_db` calls `Base.metadata.create_all`, which creates missing tables, then `models.add_missing_columns`, which adds to existing tables the model columns they lack (`ALTER TABLE … ADD COLUMN`, checked with `sqlalchemy.inspect`, idempotent, tested on SQLite and PostgreSQL). It only handles columns that accept NULL and have no server default, and refuses anything else. Renames, type changes and required columns need an explicit migration or a documented rebuild from `data/raw/`. Adopting Alembic, PostGIS or pgvector is a decision record ([ADR 0002](engineering/decisions/0002-sqlalchemy-postgres.md)).
